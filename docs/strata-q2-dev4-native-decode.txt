新 trace 与优先处理的差距
短输入 cold/hot 的 GPU decode kernel 总时长约 18.00 / 17.89 ms。
expert fast_index_copy_multi：7.47 / 7.33 ms，48 次/token，成为最大单项。
expert _grouped：3.82 / 3.83 ms，96 次/token，仍把单 token 的路由填充到 16-token tile。
BF16 GEMV：约 1.66 ms。其余压缩主干使用 FreeToken 自己的 native MMVQ。
按 GGUF 主干 native + BF16 汇总，新路径约 4.06–4.07 ms/token；此前通用 GEMM 约 88.5 ms。
1024 槽实际专家 miss 短输入约 53.1%、4K 约 58.1%；每 forward 的压缩专家 payload
约 352 / 386 MB。CPU 等待与 GPU 工作重叠，不把它们相加当作额外 GPU 时间。

缓存代码对照所得设计约束
FreeToken moe/offload_cache.py 为所有 48×512 专家保留完整 host bank，再分配 GPU cache，
当前 host source 为每层完整连续 bank，fast_index_copy.cuh 以 base + expert*stride 读取。
现有 plan_cache_budget 只规划 GPU 字节，不能代表 Windows 整机 commit 准入。
Strata src/core/expert_source.cpp 只把 GPU 未驻留的专家放进 RAM complement；
src/program/generate.cpp::resident_stage_swaps 在交换前保留被逐出的完整专家字节，
随后 commit_exchanges 维护唯一所属与正确来源。这是容量与 RAM 设计的重要差异。
FreeToken prefill 两个全层缓冲借用 cache 的低 2*512 槽；1024 槽模式没有持久 hit 区域，
不能把 prefill 热缓存等同于 decode 专家长期驻留，更不能直接把所有槽设为不可逐出。
下一轮先在现有格式与 graph 下测更大缓存的实际命中率和 decode 收益，同时监督 commit。
若容量受到完整 host bank + GPU 重复占用限制，改造应覆盖 loader、每专家 source pointer 表、
静态/动态驻留与保护、prefill D2D/host gather、reset/rebuild、交换、退出和来源验证。
不能只删除 host 字节、放大缓存或只改一个 copy kernel。
专家 decode 的另一主要方向是 Strata s2_expert_grouped.cu 的按路由、按行 DP4A 设计：
按实际专家数计算，FP32 激活 scale，压缩字节不展开为长期大权重；在独立原型中先量实际收益。
FreeToken CPU executor 当前格式表没有 q2_0，不能直接宣称已具备 Strata Q2 CPU/GPU 协同。

4096 专家槽容量实验
同一安装 wheel、graph 与固定输入，额外完成四个实际 512-token 请求。
短输入 cold/hot 为 63.13 / 64.19 tps，4K 为 62.51 / 62.73 tps。
对应相同输入的 1024 槽结果提升约 17.2%–22.5%，冷热以及跨容量完整序列均一致，质量题通过。
短输入 miss 从约 53.1% 降至 22.1%–22.5%，4K 从 58.1% 降至 24.7%–24.9%。
每 forward 的专家压缩 payload 从约 352–386 MB 降至 146–165 MB。
GPU allocated 从约 6.43 GB 增至 10.68 GB；整机 commit 峰值 65.14 GB，
最低可用 commit 5.22 GB。仅一轮四请求，不能当作重复稳定部署验收或 100 tps 结论。
数据支持优先驻留/搬运设计，同时要通过新 trace 核实大缓存的管理开销与剩余专家计算。

两种容量的 trace 补充
4096 槽短输入 cold/hot 诊断的专家 copy 为 4.29 / 2.76 ms，主干约 4.00 / 3.97 ms，
专家 grouped 约 3.83 / 3.84 ms。32-token cold 尚在缓存填充，不能替代 512-token 吞吐。
LRU 本身约 0.20–0.22 ms，没有成为新的主要瓶颈。
但 _moe_align_small 从 1024 槽约 0.248 ms 增至 4096 槽约 1.18 ms/token。
fused_q2_q8.py 把 gate_up.shape[0]（缓存槽数）传给 moe_align_block_size，
解码每层只有 10 条 route，却按全部缓存槽做专家分组统计，这是明确的规模不匹配。
下一轮专家 decode 修复应同时消除按全缓存扫描的 align、16-token padding 和串行 K group 计算，
按真实路由生成设备侧计划/直接 GEMV；prefill 保留必要的专家分组与权重复用。
可先验证仅改路由计划且保持投影算术的收益，再验证专用向量投影。不要把 LRU 和 align 混为一项。
